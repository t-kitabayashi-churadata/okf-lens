# okf-stamp 設計ドキュメント

作成: 2026-11-20 / ステータス: 設計中(実装前)

## 1. 目的とスコープ

指定したフォルダ配下の Markdown ファイル(または個別に指定したファイル)に、OKF の YAML frontmatter を付与する CLI ツール。

- 前段にエージェントを置く。エージェントが利用者に質問し、回答をマニフェスト(JSON)にまとめ、`okf-stamp` に渡す。
- `okf-stamp` は判断しない。入力された値を検証し、安全に書き込む。
- frontmatter の仕様は [okf-lens 設計ドキュメント](design.md) の 5 章と 5.1 節に従う(OKF v0.2)。
- 対象 OS は okf-lens と同じ(macOS、Windows、Linux)。

### 範囲外

- 本文の編集。frontmatter より後ろのバイト列は一切変えない。
- 予約ファイル(`index.md`、`log.md`)への frontmatter の付与(S11)。
- `type` や `tags` の推測。推測はエージェントの仕事とする。
- 語彙の登録と検証(D5 と同じ。`type` の値は制限しない)。
- インデックスやリンクの書き換え。

## 2. 決定事項

| # | 項目 | 決定 |
|---|---|---|
| S1 | 配置 | 同一リポジトリの別バイナリ `cmd/okf-stamp`。okf-lens は検索専用のまま保つ |
| S2 | 名前 | `okf-stamp` |
| S3 | 入力 | フラグ(全対象に共通の値)と JSON マニフェスト(ファイルごとの値)の両方。同じキーはマニフェストが優先する |
| S4 | 既存の値 | 3 つのモード(`fill`、`overwrite`、`merge`)から選ぶ。既定は `fill`(不足しているキーだけを補う)。どのモードにするかは、前段のエージェントが利用者と決め、マニフェストの `mode` で渡す。ツールは判断しない |
| S5 | 書き込み | 既定は dry-run。`--write` を付けたときだけ書く |
| S6 | `type` がない | そのファイルをエラーとしてスキップする。推測しない。終了コードは 3 |
| S7 | 自動補完 | しない。入力にあるキーだけを書く。`title` は okf-lens が H1 とファイル名で補う |
| S8 | 書き換え方式 | テキスト差し込み。既存の frontmatter は YAML に再エンコードせず、変更行以外をバイト単位で保つ |
| S9 | 検証の厳しさ | okf-lens は不正タグを警告して読み飛ばす。okf-stamp は書く側なので、不正値をエラーにして書かない |
| S10 | 開発環境 | okf-lens と同じ(Docker に閉じる。D12) |
| S12 | 大量ファイルの分割 | フォルダ単位で分割し、並列に実行できるようにする。`partition` が分割案を出し、`apply` は `--no-recurse` と範囲の強制で、並列実行の衝突を防ぐ。5.5 節を参照 |
| S13 | 場所の入口と境界 | 場所の入口は PATH だけ。`--dir` は作らない。境界(外へ出ない範囲)は、実行時のカレントディレクトリ。PATH はフォルダとファイルを指定でき、カレントからの相対パス(カレントの中を指す絶対パスも可)。`.okf-lensignore` とマニフェストのパスの基準も、カレントディレクトリ。【決定】2026-11-21、ユーザーが「`--dir` を廃止して PATH に一本化する」を選択。背景: 似たオプションが 2 つあると利用者が迷う。「迷いなく使える」はこのアプリの必須条件 |
| S14 | 任意キーの入口 | CLI の `--set` は作らない。専用フラグ(`--type`、`--tag`、`--alias`、`--status`)と、マニフェストだけにする。【決定】2026-11-21、ユーザーが「廃止する」を選択。背景は S13 と同じ(同じキーを指定する入口を 1 つにする) |
| S11 | 予約ファイル | `index.md` と `log.md` は、どの階層にあっても対象外。frontmatter を付与も変更もしない。根拠は 5.2 節 |

### 2.1 設計理念(判断の物差し)

設計書に記述がない場面の扱いは、次の理念から導く。「記述がないから止める」「記述がないから進める」とは決めない。理念はユーザーの発言で、【決定】。

| # | 理念 | 背景(ユーザーの発言) | 当てはめた例 |
|---|---|---|---|
| R1 | 迷いなく使える | 似たオプションが 2 つあると、使用者は迷う。そのたびに問い合わせを受けられない。迷いなく使えることは、このアプリの達成必須の条件(2026-11-21) | S13、S14(入口を 1 つにした) |
| R2 | エージェントのコンテキストに収まる量に、入力と出力を分ける | 大量のファイル(1,000〜2,000 件)では、マニフェスト(入力)も、コマンドの結果(出力)も、エージェントのコンテキストに収まらない。`partition` は、この懸念から、ファイル数を事前に調整するために作った。出どころ: 懸念は Claude が最初に挙げた(マニフェストの大きさ。1 ファイル約 150 トークン、2,000 件で約 30 万トークン)。ユーザーが「分割はコマンドのオプションで」「フォルダ単位で並列化」と指定し、2026-11-21 に「コマンドの結果がコンテキストに入らない量になる懸念」と述べた。2026-11-21 に、入力と出力の両方と確認した | 5.5 節、P11 |
| R3 | 境界の外に出ない | プロジェクトの外に出ようとするパスの指定は、防ぐ(2026-11-21) | S13、5.2 節 |

### 2.2 機能の目的の台帳

コマンドとオプションは、目的があって存在する。目的が記録されていないものを洗い出した(2026-11-21)。「出どころ」が「ユーザー」のものだけが【決定】。それ以外は、Claude が起草した目的で、ユーザーの理由は未確認。

| 機能 | 目的 | 目的の出どころ | 状態 |
|---|---|---|---|
| `apply` と PATH | 指定したフォルダ配下、または個別のファイルに、frontmatter を付与する | ユーザーの最初の依頼 | 記録済み |
| `--manifest` | 前段のエージェントの出力(ファイルごとの値)を、入力にする | ユーザーの最初の依頼と、質問「入力の形」への回答(両方) | 記録済み |
| `--type`、`--tag`、`--alias`、`--status` | 全対象に共通の値を渡す | 質問への回答(両方)。選択肢の説明は Claude | 記録済み。「マニフェストを小さくして、エージェントの文脈を圧迫しない(R2)」は Claude の説明で、2026-11-24 にユーザーが「合っている」と承認 |
| `--mode` と既定 `fill` | 既存の値の扱いを、前段のエージェントが判断して渡す。既定は不足分だけ補う | ユーザーの発言と、質問への回答 | 記録済み |
| `--write`(既定 dry-run) | 書き込む前に、結果を確認できるようにする | 質問への回答。理由は 2026-11-21 にユーザーが確認(書き込み前に結果を確認したい) | 記録済み |
| `scan` | エージェントが、全ファイルを開かずに、対象の状態(`state`、`keys`、`h1`)を把握する | Claude が起草時に提案。目的は 2026-11-21 にユーザーが確認 | 記録済み |
| `schema` | エージェントが、マニフェストを組み立てる手がかり | 同上 | 記録済み |
| `partition`、`--max-files`、`--no-recurse` | R2 のとおり | 懸念は Claude、方式はユーザー | 記録済み(R2 は入力と出力の両方) |
| `--max-files` の既定 100 | 1 グループの出力が、コンテキストに収まる量にする | Claude の見積もり。100 ファイルで `apply` の JSON は 33KB(実測)。2026-11-21 にユーザーが「100 のままでよい。実際の作業で調整する」と決定 | 記録済み。調整は実作業の結果で行う |
| `--exclude` | okf-lens と同じ書式で、対象から外す | okf-lens に揃えた。2026-11-21 にユーザーが承認 | 記録済み |
| `--format`(table、json) | 人が読む形と、エージェントが読む形 | okf-lens に揃えた。2026-11-21 にユーザーが承認 | 記録済み |
| `--verbose` | スキップの理由を 1 件ずつ見る | okf-lens に揃えた。2026-11-21 にユーザーが承認 | 記録済み |
| 終了コード 3 | エージェントが、質問してやり直す合図 | `type` がないファイルの扱い(エラーでスキップ)はユーザーが選択。コード番号は Claude。合図の役割は 2026-11-21 にユーザーが承認 | 記録済み |
| `changes`(旧 `--diff`) | `--write` の前に、上書きで何がどう変わるかを見る | P9 でユーザーが選択 | 記録済み(14 章 P9)。旧 `--diff` は、目的が記録されないまま作られ、欠陥が出た例 |
| `legacy_key` の警告 | `--where` の任意キー検索のため、単数形のキーを利用者が使う可能性を残す | ユーザーの発言 | 記録済み(6.1 節) |

## 3. 全体の流れ

```
利用者 ⇄ エージェント ──(マニフェスト JSON)──▶ okf-stamp ──▶ .md ファイル
              │                                    │
              └──── okf-lens types / scan ◀────────┘(語彙と現状の確認)
```

エージェントの標準手順は次のとおり。

| 手順 | 操作 | 使うもの |
|---|---|---|
| 1 | 対象フォルダの現状を取得する | `okf-stamp scan`(7 章) |
| 2 | 既存の `type` の語彙を取得する | `okf-lens types` |
| 3 | 利用者に質問し、`type`、`tags` などを決める | エージェント |
| 4 | マニフェストを作り、dry-run する | `okf-stamp apply --manifest m.json --format json` |
| 5 | 結果を利用者に見せる。終了コード 3 なら入力を直して 4 に戻る | エージェント |
| 6 | 利用者の承認後、`--write` を付けて実行する | `okf-stamp apply ... --write` |
| 7 | 反映後、読み飛ばしが 0 件になったことを確認する | `okf-lens types`(標準エラー出力の読み飛ばし件数) |

## 4. アーキテクチャ

```
cmd/okf-stamp         引数解析、レポート整形
   │
internal/stamp        マニフェスト読み込み、計画(Plan)の作成、検証、書き込み
   │
internal/okf          frontmatter の生分割(新規)、タグ検証(公開に変更)
internal/source       ファイル列挙(新規 List。パース前の候補を返す)
```

- 処理は「計画 → 検証 → 書き込み」の3段階に分ける。dry-run は書き込みの手前で止める。
- 既存コードへの変更は最小にする。

| 既存 | 変更 |
|---|---|
| `internal/okf/parse.go` の `validTag` | `ValidTag` として公開する |
| `internal/okf/parse.go` の `splitFrontmatter` | バイトオフセットを返す `SplitRaw` を追加する。`Parse` は変えない |
| `internal/source` | パースせずに候補ファイルを返す `List` を追加する。`index.md`、`log.md`、`.` 始まりのディレクトリ、`.okf-lensignore`、`--exclude` の規則は `Scan` と共有する |
| `internal/cli` | 変更しない。`okf-stamp` は `parseInterspersed` と同じ流儀で `internal/stamp/cli` に別実装する |

`Scan` は、frontmatter がないファイルを読み飛ばしとして捨てる。okf-stamp はそのファイルこそ対象にするため、`List` が必要になる。

## 5. CLI 仕様

```
okf-stamp apply [PATH...] [フラグ]
okf-stamp scan  [PATH...] [フラグ]
okf-stamp partition [PATH...] [フラグ]
okf-stamp schema
okf-stamp version
okf-stamp help
```

### 5.1 `apply` のフラグ

| フラグ | 意味 |
|---|---|
| `PATH...` | 対象のディレクトリまたはファイル。複数指定できる。ディレクトリは再帰的に走査する |
| `--manifest <file\|->` | マニフェスト。`-` で標準入力。6 章を参照 |
| `--type <type>` | 全対象に共通の `type` |
| `--tag <tag>` | 全対象に共通のタグ。繰り返し指定する。カンマ区切りは受け付けない |
| `--alias <alias>` | 全対象に共通の別名。繰り返し指定する |
| `--status <status>` | `draft`、`stable`、`deprecated` のいずれか |
| `--mode <fill\|overwrite\|merge>` | 既存の値の扱い。既定は `fill`。マニフェストの `mode` が優先する。8.2 節を参照 |
| `--write` | ファイルに書き込む。指定しないときは dry-run |
| `--no-recurse` | ディレクトリの直下の `.md` だけを対象にする。サブフォルダは見ない(5.5 節) |
| `--exclude <pattern>` | 除外するファイルやディレクトリ。okf-lens と同じ書式(7.1 節) |
| `--format <table\|json>` | 出力形式。既定は `table` |
| `--verbose` | スキップしたファイルの理由を1件ずつ表示する |

### 5.2 対象ファイルの決定

対象は「PATH 引数を展開したファイル」と「マニフェストに載るファイル」の和集合。

| 指定 | 扱い |
|---|---|
| ディレクトリ | 配下の `.md` を再帰的に列挙する。予約ファイル(下記)、`.` 始まりのディレクトリ、`.okf-lensignore`、`--exclude` は除く。除いたファイルはレポートに出さない |
| ファイルを直接指定 | `.okf-lensignore` と `--exclude` は適用しない(利用者の明示的な意図を優先)。予約ファイルは適用せず、`skip`(`reserved_name`)として報告する |
| マニフェストのパス | 直接指定と同じ扱い。エージェントの指定ミスを知らせるため、`skip` にして終了コード 3 を返す |
| PATH 指定があるとき、範囲外のマニフェストのパス | `skip`(`outside_scope`)にして終了コード 3 を返す。並列実行で、別の担当のフォルダを触る事故を防ぐ(5.5 節) |
| 境界(カレントディレクトリ)の外を指す PATH | 何も処理せず、終了コード 2 で止める。`..` や、カレントの外を指す絶対パスを含む。コマンド自体の誤りのため |
| 存在しない PATH | 何も処理せず、終了コード 2 で止める。打ち間違いは、コマンド自体の誤りのため。14 章 P10(承認済み) |
| マニフェストのパスが、境界の外、存在しない、`.md` 以外 | その行だけ `skip`(`outside_root`、`not_found`、`not_markdown`)にして、終了コード 3 を返す。ファイルごとのデータの誤りのため |

#### 予約ファイル(S11)

| 項目 | 内容 |
|---|---|
| 対象 | ファイル名が `index.md` または `log.md` のもの。どの階層でも、大文字小文字を区別せず(D9)判定する |
| 根拠 | OKF v0.2 は、`index.md` に frontmatter を置かないと定める(§8)。例外はバンドルルートの `index.md` に置く `okf_version` だけ(§12)。`log.md` は予約名で、concept の frontmatter 要件(§11)の対象外 |
| 挙動 | 付与も変更もしない。ルートの `index.md` にある `okf_version` の frontmatter も、そのまま残す |
| 判定の共有 | okf-lens の `Scan` と同じ判定関数を使う(`internal/source`)。仕様の解釈を2か所に持たない |
| 注意 | 予約名のファイルに `type` を付けると、concept として扱われ、リンク元の集計(D19)や検索結果に混ざる |

### 5.3 値の優先順位

```
マニフェストの files[].frontmatter  >  フラグ(--type、--tag など)  >  ファイルの既存の値(mode が overwrite または merge のときだけ変わる)
```

- キー単位で解決する。値の中身はマージしない。`tags` をマニフェストで指定したら、フラグの `--tag` は無視する。
- 既存の値との関係は 8 章を参照。

### 5.5 分割と並列実行(S12)

1,000〜2,000 件のフォルダを、エージェントがフォルダ単位に分けて、並列(サブエージェントなど)に処理する運用を想定する。ツールは、分割案の作成と、並列実行の安全を担う。

```
partition ──▶ グループ一覧 ──▶ グループごとに worker が apply(並列)──▶ 各レポートを集約
```

#### `partition`

```
okf-stamp partition [PATH...] [--max-files N] [--exclude <pattern>] [--format table|json]
```

対象を、互いに重ならないグループに分ける。1グループは、ファイル数が `--max-files`(既定 100)以下になるようにする。

| 規則 | 内容 |
|---|---|
| 基本 | フォルダを1グループにする(再帰的に配下を含む) |
| 上限超過 | サブフォルダごとに分ける。そのフォルダの直下のファイルは、別グループ(`recursive: false`)にする |
| 分けられない | 直下のファイルだけで上限を超えるフォルダは、`oversize: true` で報告する。エージェントが、マニフェストを複数に分けて対処する |
| 数える対象 | `apply` の対象になるファイル(予約ファイルと除外指定を除く) |
| 決定的 | 同じ入力で、同じ分割になる(パスの辞書順) |
| ファイルの PATH | そのファイル 1 つを、`recursive: false`、`files: 1` のグループにする(フォルダの PATH の配下にあるファイルは重複させない)。対象外のファイルは、グループにしない |

```json
{
  "total": 1850,
  "groups": [
    { "path": "api",        "recursive": true,  "files": 92 },
    { "path": "screen",     "recursive": false, "files": 40 },
    { "path": "screen/pc",  "recursive": true,  "files": 85 },
    { "path": "docs/spec",  "recursive": false, "files": 640, "oversize": true }
  ]
}
```

worker は、グループごとに次のように実行する。

```
okf-stamp apply api --manifest api.json --format json
okf-stamp apply screen --no-recurse --manifest screen.json --format json
```

#### 並列実行の安全

| 項目 | 規則 |
|---|---|
| 範囲の強制 | PATH を指定した実行は、範囲外のマニフェストのパスを `outside_scope` にして触らない。worker が自分の担当の外を書き換えない |
| 重ならない担当 | `partition` のグループは重ならない。エージェントが独自に分けるときも、重ならないようにする(`docs/` と `docs/api/` を別々の worker に渡さない) |
| 重なった場合 | ファイル単位の原子的な書き込みと、書き込み直前の再確認(8.3 節)で、後から書く側が `changed_during_run` になる。壊れないが、失敗する |
| ロック | 作らない。上の対策で足りる |
| 集約 | レポートは実行ごとに出る。JSON に `scope`(`path`、`recursive`)を含める。エージェントが、グループごとの結果を集約する |
| 終了コード | 各 worker が個別に返す。エージェントは、3 の worker だけを入力修正して再実行する。冪等なので、完了したグループは再実行しても影響しない |

件数で分ける `--limit` や `--offset` は作らない。実行ごとに対象がずれ、冪等性と再現性が下がるため。

### 5.4 終了コード

| コード | 意味 |
|---|---|
| 0 | 正常終了。変更なし(すべて `unchanged`)を含む |
| 1 | 実行エラー(ディレクトリがない、書き込み失敗など) |
| 2 | 引数エラー(不明なフラグ、不正な `--format`、マニフェストの書式違い、境界の外または存在しない PATH など) |
| 3 | 一部のファイルを入力エラーでスキップした。エラーのないファイルは、dry-run なら計画どおり、`--write` なら書き込み済み |

終了コード 3 は、エージェントが質問してやり直す合図にする。dry-run でも同じ規則で返すため、エージェントは書き込む前に不足を検出できる。

## 6. マニフェスト(エージェントとの契約)

```json
{
  "version": 1,
  "mode": "fill",
  "files": [
    {
      "path": "api/auth.md",
      "mode": "merge",
      "frontmatter": {
        "type": "API",
        "title": "認証API",
        "description": "ログイン時のトークン発行 API",
        "tags": ["設計/基本設計"],
        "aliases": ["Auth API"],
        "status": "draft"
      }
    },
    {
      "path": "screen/login.md",
      "frontmatter": { "type": "画面" }
    }
  ]
}
```

| 項目 | 規則 |
|---|---|
| `version` | 必須。現在は `1`。未知の値はエラー(終了コード 2) |
| `mode` | 任意。全ファイルの既定のモード。`fill`、`overwrite`、`merge` のいずれか。省略時は `fill`(`--mode` の値) |
| `files[].mode` | 任意。そのファイルのモード。トップレベルの `mode` より優先する。キー単位の指定はできない(ファイル単位) |
| `files[].path` | 必須。カレントディレクトリからの相対パス。`\` は `/` に変換する。NFC と NFD の違いは吸収する |
| `files[].frontmatter` | 必須。キーは OKF のキー、または任意の追加キー。値は JSON の型をそのまま YAML にする(ネスト可) |
| 未知のトップレベルキー | エラー(終了コード 2)。エージェントの綴り間違いを早く検出するため |
| 同じ `path` の重複 | エラー(終了コード 2) |
| `frontmatter` の中の未知のキー | 拒否しない(OKF の規則)。そのまま書く |

エージェント向けに `okf-stamp schema` が JSON Schema を標準出力に出す。エージェントは、これを読んでマニフェストを組み立てられる。

### 6.1 値の検証

検証に失敗したファイルは、そのファイルだけをスキップする(S6、S9)。

| キー | 規則 |
|---|---|
| `type` | 書き込み後の frontmatter に必須。空でない文字列。値の語彙は検証しない(D5) |
| `tags` | 文字列のリスト。先頭の `#` は除去する。Obsidian のタグ規則(`okf.ValidTag`)に反する値はエラー |
| `aliases` | 文字列のリスト。空要素はエラー |
| `status` | `draft`、`stable`、`deprecated` のいずれか |
| `stale_after` | RFC 3339 で、UTC オフセット付き(OKF §5 の要件)。YAML には引用符なしの日時として書く(例: `stale_after: 2026-12-31T00:00:00Z`)。okf-lens の `--where` が日時型を RFC 3339 表記で比較するため、この形が自然。既存の引用符なしの値と同じ表記になり、`overwrite` を再実行しても書き直しは起きない。既存が引用符つきの文字列なら、`overwrite` で日時型に直す |
| キー名 `tag`、`alias`(単数形) | 警告(`legacy_key`)を付けて、そのまま書く。複数形の `tags`、`aliases` とは別のキー。okf-lens は専用キーとして読まず、任意キーとして扱う([okf-lens 設計ドキュメント](design.md) 5 章「旧キー」)。このため `--tag` と別名検索の対象にならず、`--where tag=...` でだけ検索できる(同 D8、4.2 節)。【決定】2026-11-20、ユーザーが「警告して書く」を選択。背景もユーザーの説明による: okf-lens に任意キー検索(`--where`)があるため、利用者が単数形を意図して使う場合がある。`tags`、`aliases` の中身の規則とは別の検査 |
| `title`、`description`、`resource` | 空でない文字列 |
| その他 | 検証しない |

- 文字列はすべて NFC に正規化して書く。
- 文字列以外の値(数値、真偽値、日付に見える文字列)は、YAML で型が変わらないよう、必要なときだけ引用符を付ける(例: `"2026-11-20"` を文字列として書く場合)。

## 7. `scan`(エージェントの現状確認用)

エージェントが全ファイルを開かなくても、対象の状態を把握できるようにする。実装は第2段階とする(12 章)。

```
okf-stamp scan [PATH...] [--no-recurse] [--exclude <pattern>] [--format table|json]
```

| `state` | 意味 |
|---|---|
| `ok` | frontmatter があり、`type` がある |
| `no-type` | frontmatter はあるが `type` がない |
| `no-frontmatter` | frontmatter がない |
| `broken` | frontmatter の YAML が不正、または終端の `---` がない。`apply` は触らない |

JSON の各要素は `path`、`state`、`keys`(既存のトップレベルキー)、`h1`(本文の最初の H1)を持つ。エージェントは `h1` を見て、`title` を書くかどうかを利用者に確認できる。

## 8. 書き換えの仕様

### 8.1 方針

okf-lens の `Parse` は、CRLF や BOM を正規化し、YAML をマップに読み込む。書き換えにはこの結果を使わない。YAML に再エンコードすると、既存のキー順、コメント、引用符、インデントが変わり、Git の差分が肥大するため。

| 項目 | 方式 |
|---|---|
| 生分割 | `okf.SplitRaw` で、BOM、frontmatter、本文の位置をバイトオフセットで得る |
| キーの追加 | 閉じ側の `---` の直前に、新しいキーの行を差し込む。既存の行は1バイトも変えない |
| キーの上書き(mode が `overwrite` または `merge`) | `yaml.Node` の行番号で、そのキーの行範囲(次のキーの前まで)を特定し、その範囲だけ置き換える |
| 新しい値の YAML 化 | `yaml.v3` で1キーのマップをマーシャルして得る。引用符や日本語の扱いは任せる |
| 改行コード | ファイルの既存の改行(LF または CRLF)に合わせる。BOM も残す |
| 本文 | 一切変えない |
| ファイル末尾の改行 | 既存のまま |

### 8.2 ケース別の挙動

| 既存の状態 | `fill`(不足分を補う) | `overwrite`(入力で置き換える) | `merge`(リストは和集合) |
|---|---|---|---|
| frontmatter がない | 新しい frontmatter を、ファイルの先頭に作る | 同左 | 同左 |
| frontmatter があり、キーがない | 入力のキーを末尾に追加する | 同左 | 同左 |
| スカラのキーが既にある(`type`、`title` など) | 既存を残す(`kept`) | 入力の値で置き換える | 既存を残す(`kept`) |
| `tags`、`aliases` が既にある | 既存を残す | 入力で置き換える | 既存の要素の後ろに、入力の新しい要素を足す。重複は NFC、大文字小文字を区別せず判定して除く |
| ネストしたキー(`sources` など)が既にある | 既存を残す | 入力で置き換える | 既存を残す |
| 空の frontmatter(`---` と `---` だけ) | キーを追加する | 同左 | 同左 |
| 終端の `---` がない、YAML が不正 | `broken` としてスキップする。ファイルは変えない | 同左 | 同左 |
| UTF-8 でない | エラーとしてスキップする | 同左 | 同左 |
| 改行が CR だけのファイル | `broken_frontmatter` としてスキップする。okf-lens の `Parse` は CR を改行として読めるが、`SplitRaw` はバイト位置で frontmatter を切り出すため、CR だけの改行を行として数えない。放置すると「frontmatter なし」と誤判定し、既に frontmatter があるファイルに 2 つ目を付けて壊す。旧 Mac OS の形式で、実在する可能性は極めて低い | 同左 | 同左 |

`merge` は「既存のスカラを守りつつ、タグだけ足す」用途のモード。`merge` でスカラも更新したい場合は、`overwrite` にして、`tags` に既存の値を含めてマニフェストを作る(エージェントが `scan` などで既存の値を知っている前提)。

- 新規作成のキー順は、`type`、`title`、`description`、`resource`、`tags`、`aliases`、`status`、`stale_after`、残りは辞書順。
- 新しい frontmatter の直後と本文の間に、空行を1行入れる(本文が空でないとき)。
- 冪等にする。同じ入力で再実行すると、すべて `unchanged` になる。
- 先頭が `---` で始まる本文(水平線)に、終端がない場合は `broken` と判定し、触らない。frontmatter を誤って付けて本文を壊す事故を避ける。

### 8.3 書き込みの安全策

| 項目 | 対策 |
|---|---|
| 原子性 | 同じディレクトリの一時ファイルに書き、`rename` で置き換える。途中で失敗しても、元のファイルは残る |
| 権限 | 元のファイルのパーミッションを引き継ぐ |
| 競合 | 計画時のファイル内容のハッシュを保持し、書き込み直前に再読み込みして比較する。変わっていたら、そのファイルをエラーとしてスキップする |
| 部分適用 | ファイル単位で独立に処理する。1つが失敗しても、他は続ける(終了コード 3 または 1) |
| 書き込み前の確認 | 新しい内容をメモリ上で組み立て、`okf.Parse` に渡して検証する。`type`、`tags`、`aliases` が入力どおり読めなければ、ファイルには何も書かず、エラーにする。確認が通った内容だけを一時ファイルに書く。`tags` と `aliases` の厳密な比較は、入力の値だけで書いたキー(新規追加と `overwrite` での置き換え)に限る。`merge` は既存の要素を含むので、比較しない |
| シンボリックリンク | リンク先がカレントディレクトリの外なら、そのファイルを `skip`(`outside_root`)にする |

## 9. 出力

標準出力に結果だけを書き、件数と警告は標準エラー出力に書く(okf-lens と同じ)。

### 9.1 table

```
ACTION     PATH              DETAIL
add        api/auth.md       +type +title +tags
update     screen/login.md   +tags (kept: type)
unchanged  api/token.md
skip       memo/idea.md      type がない
```

| ACTION | 意味 |
|---|---|
| `add` | frontmatter を新規に作る |
| `update` | 既存の frontmatter にキーを追加、または上書きする |
| `unchanged` | 変更なし |
| `skip` | 入力エラーまたは `broken`。DETAIL に理由を書く |

dry-run のときは、標準エラー出力に `dry-run: ファイルは変更していません。--write で反映します` を出す。

### 9.2 json

```json
{
  "dry_run": true,
  "scope": { "paths": ["api"], "recursive": true },
  "summary": { "add": 1, "update": 1, "unchanged": 1, "skip": 1 },
  "files": [
    {
      "path": "api/auth.md",
      "action": "add",
      "kept": [],
      "errors": [],
      "warnings": [],
      "changes": [
        { "key": "type", "after": "API" },
        { "key": "status", "before": "draft", "after": "stable" }
      ]
    },
    {
      "path": "memo/idea.md",
      "action": "skip",
      "errors": [{ "code": "missing_type", "message": "type がない" }]
    }
  ]
}
```

- JSON はインデントなしの 1 行で出す(R2。100 ファイルで 77KB を 33KB にした)。`added` と `overwritten` は出さない。`changes` に、新しく書いたキー(`before` なし)と、上書きしたキー(`before` あり)の両方が入る。
- `changes` は、書いたキー(dry-run では書くキー)ごとに、変更前(`before`)と変更後(`after`)の値を出す。新しく書いたキーは `before` を省く。値が同じで書かなかったキーは出さない。常に出す(フラグはない)。table 形式では、上書きしたキーを DETAIL に `~type(Memo→API)` と出す(30 文字を超える値は省略する)。
- `warnings` は `errors` と同じ形(`code`、`message`)で、書き込みは止めない注意を入れる。table 形式では、DETAIL に `warn: legacy_key` と出す。
- `errors[].code` は機械可読にする。エージェントが、次の質問を決める手がかりにする。

| code | 意味 |
|---|---|
| `missing_type` | `type` がない |
| `invalid_tag` | タグが規則に反する |
| `invalid_status` | `status` が列挙値でない |
| `invalid_value` | その他のキーの値が不正 |
| `legacy_key`(警告) | `tag`、`alias`(単数形)を使っている。書き込みは行い、`warnings` に出す。メッセージで、`--where` でだけ検索できることと、複数形の誤りなら直すことを伝える |
| `broken_frontmatter` | 既存の frontmatter が壊れている |
| `not_found` | ファイルがない |
| `reserved_name` | `index.md` または `log.md` |
| `outside_root` | 境界(カレントディレクトリ)の外を指す。マニフェストのパス、またはシンボリックリンクの先 |
| `outside_scope` | PATH 指定の範囲の外を指すマニフェストのパス |
| `not_utf8` | UTF-8 でない |
| `changed_during_run` | 計画後に、ファイルが変更された |
| `write_failed` | 書き込みに失敗した(一時ファイルの作成、`rename` の失敗など)。終了コードは 1(5.4 節)。【私の判断】14 章を参照 |

## 10. テスト方針

| 対象 | 観点 |
|---|---|
| 差し込み | 既存の frontmatter の行が1バイトも変わらない。コメント、引用符、キー順が残る |
| 改行 | LF、CRLF、BOM 付きのファイルで、元の改行と BOM を保つ |
| 冪等 | 2回目の実行で、すべて `unchanged` になる |
| 往復 | 書いた結果を `okf.Parse` で読み直し、入力の値と一致する(`type`、`tags`、`aliases`) |
| モード | `overwrite` で対象キーの行範囲だけが変わる。複数行の値(リスト、ネスト)を置き換えられる。`merge` でタグが和集合になり、重複が出ない。ファイルごとの `mode` が全体の `mode` に勝つ |
| 検証 | 6.1 節の各エラーコードが出る。エラーのファイルは変更されない |
| 優先順位 | マニフェスト > フラグ > 既存。キー単位で解決される |
| パス | `..`、絶対パス、シンボリックリンク、NFC と NFD の違い、`\` 区切り |
| 競合 | 計画後にファイルを書き換えると、`changed_during_run` になる |
| 分割と並列 | `partition` のグループが重ならず、合計がすべての対象ファイルと一致する。`--no-recurse` がサブフォルダを見ない。`outside_scope` が範囲外を書かない。2つの `apply` を同時に走らせても、重ならないフォルダなら結果が逐次実行と同じになる |
| 原子性 | 書き込みの途中失敗で、元のファイルが残る |
| OS | okf-lens と同じ matrix(macOS、Windows、Ubuntu)で CI を回す。特に Windows の `rename` による置換と CRLF |

## 15. エージェント側(Skill)

`.claude/skills/okf-stamp/SKILL.md`。okf-stamp を使う作業の手順を、エージェントに渡す。

### 15.1 目的と使われ方

【決定】2026-11-21、ユーザーが説明した実作業は、次の流れ。

1. すでに大量の md がある `dev` ブランチから、stamp 作業用のベースブランチを切る。
2. 全体の方針を、作業ブランチに置く。
3. 各人が、方針に従い、フォルダ単位などで作業して commit する。
4. 作業ブランチに取り込み、最後に `dev` へ戻す。

この作業は、**別のリポジトリ**で行う。そのため、Skill は 2 つの動作モードを持つ。

| モード | 使う人 | やること |
|---|---|---|
| 全体の方針を決める | 作業の責任者 | `scan`、`partition`、`okf-lens types` で現状を調べ、方針の項目を聞き、方針ファイルを書く |
| 担当フォルダを処理する | 各担当者 | 方針ファイルを読み、担当の PATH を `partition` で分け、グループごとに値を聞き、dry-run、承認、`--write` の順で処理する |
