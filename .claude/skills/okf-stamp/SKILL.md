# okf-stamp の運用

`okf-stamp` は、`.md` ファイルに OKF の YAML frontmatter を書く CLI。判断はしない。`type` やタグを決めるのは、このスキルと利用者の仕事。

## 前提

- `okf-stamp` と `okf-lens` が PATH にある。確認: `okf-stamp version`、`okf-lens version`。ないときは、利用者に伝えて止める。
- カレントディレクトリが境界。PATH はカレントの中だけを指せる。作業するリポジトリのルートで実行する。
- 質問は `AskUserQuestion` で行う。1 回に最大 4 問まで、まとめて聞ける。推測で `type` やタグを決めない。
- `scan`、`partition`、`apply` の JSON は、標準出力に出る。人向けの 1 行の集計は、標準エラー出力に出る。JSON はファイルにリダイレクトして、件数だけを読む。
- `index.md` と `log.md`(OKF の予約ファイル)と、`.md` 以外のファイルは対象外。`scan` と `partition` の件数に含まれない。
- git の操作(ブランチ作成、commit、merge、push)は一切しない。ファイルを書き換えるところまでを行い、commit は利用者に任せる。

## 守ること(設計理念)

| 理念 | スキルでの行動 |
|---|---|
| 迷いなく使える | 質問は選択肢を示し、推奨を先頭にする。同じことを 2 回聞かない |
| 出力がコンテキストに収まる量 | `scan` と `apply` の結果を、丸ごと表示しない。件数と、問題のあるファイルだけを要約する。大量のときは `partition` で分けたグループ単位で扱う |
| 境界の外に出ない | PATH はカレントの中だけ。`..` で外へ出ない |

## 最初の質問

`AskUserQuestion` で、動作モードを聞く。

| モード | 使う人と場面 |
|---|---|
| 全体の方針を決める | 作業全体の責任者。担当者が従う、共通の方針ファイルを作る |
| 担当フォルダを処理する | 各担当者。方針ファイルに従い、自分のフォルダに frontmatter を付ける |

## モード A: 全体の方針を決める

1. 対象の範囲(PATH)を聞く。
2. 現状を調べる。
   - `okf-stamp scan <PATH> --format json` の結果から、`state` ごとの件数を数える(`ok`、`no-type`、`no-frontmatter`、`broken`)。
   - `okf-stamp partition <PATH> --format json` で、フォルダごとのファイル数を見る。
   - 一覧は表示しない。件数と、`broken` のファイルのパス(多いときは先頭 10 件)だけを報告する。利用者が詳細を求めたら出す。
3. 既存の `type` を調べる。`okf-lens types --dir <PATH>`。件数付きで出る。`API` と `api` のような表記の揺れがあれば、利用者に示す。
4. 方針の項目を聞く。関連する項目は、1 回の `AskUserQuestion`(最大 4 問)にまとめる。

   | 項目 | 聞くこと | 選択肢 |
   |---|---|---|
   | 既存の値の扱い(`mode`) | 既に frontmatter があるファイルの値をどうするか | `fill`(不足だけ補う。推奨)、`overwrite`(入力で置き換える)、`merge`(`tags` と `aliases` は足し、それ以外は既存を残す) |
   | `type` の語彙 | 使ってよい `type` と表記 | 手順 3 で出た既存の `type`、または新しい `type` |
   | `type` の統一 | 手順 3 で表記の揺れ(`api` と `API` など)が出たとき、どの表記に統一するか | 統一する(旧 → 新)、統一しない |
   | タグの規則 | 付けるタグの形 | 階層を使うか(`設計/基本設計`)、先頭の `#` なし。空白と `.` は使えない |
   | `status` の既定 | 付けるか | 付けない、`draft`、`stable`、`deprecated` |
   | フォルダと `type` の対応 | フォルダごとに `type` が決まるか(任意) | 決まる、決まらない |
   | `title` | 付けるか | 付けない(既定。H1 とファイル名から、okf-lens が補う)、付ける |

5. 方針ファイルの保存先を聞き、書く。形式は次のとおり。対象の `.md` の中に置くと、`scan` などの対象に入る。その場合は、モード B で `--exclude <方針ファイルのパス>` を付けると伝える。
6. 終わりに、利用者に次を伝える。
   - 方針ファイルを書いた場所。
   - 担当者は、モード B でこのファイルを指定する。
   - 作業ブランチを `dev` に戻す前に、方針ファイルを削除する。
   - commit は利用者が行う。

### 方針ファイルの形式

```markdown
# okf-stamp 方針

## 既存の値の扱い
mode: fill

## type
| type | 使う場面 |
|---|---|
| API | API の仕様書 |
| 画面 | 画面設計書 |

## タグの規則
- 階層は `/` で区切る(例: `設計/基本設計`)
- 先頭の `#` は付けない

## status の既定
status: draft

## フォルダと type の対応
| フォルダ | type |
|---|---|
| api | API |
| screen | 画面 |

## type の統一
| 旧 | 新 |
|---|---|
| api | API |

## title
title: 付けない
```

「フォルダと type の対応」と「type の統一」は、ないときは表を空にする。`status` を付けないときは `status: なし`。

## モード B: 担当フォルダを処理する

1. 方針ファイルのパスを聞き、読む。読めなければ、利用者に伝えて止める。
2. 担当の PATH を聞く(複数可)。
3. 現状を調べる。`okf-stamp scan <PATH...> --format json` から、`state` ごとの件数だけを報告する。`broken` のファイルは、触らないと伝える(利用者が YAML を直してから再実行する)。方針ファイルが PATH の配下にあるときは、`--exclude <方針ファイルのパス>` を付ける。以降のコマンドも同じ。
4. 方針に「type の統一」があるときは、先に統一する(次の「type の統一」)。
5. `okf-stamp partition <PATH...> --format json` で、グループに分ける。1 グループが処理の単位。
   - `recursive: true`: そのフォルダの配下すべて。
   - `recursive: false`: そのフォルダの直下のファイルだけ。配下のファイル数が `--max-files`(既定 100)を超えるフォルダは、直下のファイルと、サブフォルダのグループに分かれる。
   - `oversize: true`: 直下のファイルだけで上限を超えている。手順 7 の「oversize のグループ」に従う。
6. グループごとに、付ける値を決める。
   - 方針の「フォルダと type の対応」に当たるグループは、その `type` を使う。
   - 当たらないグループは、`scan` の `h1` とパスを見て、利用者に `type` とタグを聞く。選択肢は、方針の `type` の一覧。
   - 方針にない `type` やタグが必要になったら、利用者に確認する。許可されたら書く。許可された値は、「方針にない値」として記録する。
7. 値を渡す。
   - グループの全ファイルに共通の値は、フラグ(`--type`、`--tag`、`--alias`、`--status`)で渡す。
   - ファイルごとに違う値(`title` など)は、マニフェスト(JSON)に書く。形式は `okf-stamp schema`。マニフェストは、リポジトリの外の一時ファイルに置く。
   - 既存の値の扱いは、方針の `mode`。フラグは `--mode`、マニフェストは `mode`。方針の `status` が「なし」のときは、`--status` を付けない。
   - **oversize のグループ**: 結果が大きくなるため、PATH を渡さず、マニフェストだけで分ける。`scan` の結果のパスを辞書順に 100 件ずつ分け、`files[].frontmatter` を `{}` にしたマニフェストを作る。共通の値は、`--type` などのフラグで渡す。例: `okf-stamp apply --manifest m1.json --type 仕様`。マニフェストを渡す実行では、マニフェストのファイルだけが対象になる。
8. dry-run で確認する。`--write` を付けずに実行する。
   - 再帰的なグループ: `okf-stamp apply <path> <値のフラグ> --format json`
   - `recursive: false` のグループ: `okf-stamp apply <path> --no-recurse <値のフラグ> --format json`
   - 結果は、`summary`(件数)と、`action` が `skip` のファイルの `errors[].code` の件数だけを報告する。
   - 終了コード 3 は、一部のファイルを `skip` した合図。`skip` でないファイルは、計画どおり(`--write` なら書き込み済み)。理由の `code` で扱いを分ける。
     - `broken_frontmatter`、`not_utf8`: 利用者が直すまで `skip` のまま。直さないと決めたなら、想定内として進める。
     - ほかの `code`: 入力を直して再実行する。
   - `skip` がある場合は、内訳を利用者に示してから、手順 9 に進む。
   - `warnings` に `legacy_key`(キー名が単数形の `tag`、`alias`)があれば、利用者に示す。`tags`、`aliases` の誤りなら直す。
9. 利用者の承認を得て、同じコマンドに `--write` を付けて実行する。冪等なので、再実行しても影響しない。
10. 終わりに、次を報告する。
   - 処理したグループと、件数(`add`、`update`、`unchanged`、`skip`)。
   - `skip` したファイルと、理由の `code`。
   - 方針にない値を使ったファイルの一覧。方針の責任者に伝える。
   - commit は利用者が行う。

### type の統一

方針に「type の統一(旧 → 新)」があるときの手順。

1. `okf-lens search --type <旧> --dir . --format json` で探す。`--type` は大文字小文字を区別しないため、結果の `type` が旧の表記と完全に一致するものだけを選ぶ。担当の PATH の配下のパスだけを使う。
2. 該当ファイルを `files[].mode` を `overwrite`、`frontmatter` を `{"type": "<新>"}` にしたマニフェストにする。PATH は渡さない。
3. dry-run(`okf-stamp apply --manifest <file>`)の結果を、変更前後(`~type(api→API)`)で利用者に示し、承認を得て `--write` を付けて実行する。
4. 統一したファイル数を、最後の報告に含める。

### グループが複数あるとき

- 質問は、親(このスキルを実行している側)がすべて先に済ませる。サブエージェントには、利用者への質問をさせない。
- dry-run(手順 8)は、親が実行して結果を要約する。承認(手順 9)のあと、`--write` をグループごとにサブエージェントに並列で実行させる。同時に動かす数は最大 10。グループが 10 以下なら、グループごとに 1 つ。利用者が数を指定したら、それに従う。
- サブエージェントには、実行するディレクトリ、PATH の設定(`okf-stamp` が PATH にあること)、実行するコマンドを渡す。
- サブエージェントには、担当のグループの PATH だけを渡す。範囲外のマニフェストのパスは、`outside_scope` でスキップされる。
- サブエージェントは、結果を件数と `skip` の理由だけで返す。
- グループは重ならない。`partition` の結果をそのまま使う。独自に分けるときは、`docs/` と `docs/api/` のように重ならないようにする。

## エラーコード(`errors[].code`)

| code | 意味 | 対応 |
|---|---|---|
| `missing_type` | 最終的なファイルに `type` がない | `type` を決めて再実行 |
| `invalid_tag`、`invalid_status`、`invalid_value` | 入力の値が不正 | 値を直す |
| `broken_frontmatter` | 既存の YAML が不正、または終端の `---` がない | 触らない。利用者が直す |
| `reserved_name` | `index.md`、`log.md`(OKF の予約ファイル) | 対象外。付けない |
| `outside_scope` | PATH の範囲の外 | 担当の範囲を見直す |
| `outside_root` | カレントの外、またはリンク先が外 | 対象外 |
| `changed_during_run` | 実行中にファイルが変わった | 再実行 |
| `not_found`、`not_markdown`、`unreadable` | ファイルがない、`.md` ではない、読めない | パスを見直す |
| `not_utf8` | UTF-8 ではない | 触らない。利用者が直す |
| `verify_failed`、`write_failed` | 書く内容の検証に失敗、または書き込みに失敗 | 利用者に報告する(終了コード 1 になる) |
